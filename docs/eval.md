# Evaluation of the LLM tasks

**No evaluation has been run yet.** There is no LLM key in the environment that built this repository, so every LLM value shown in the
README, the report and the media is a scripted answer from the fake provider. LLM proposal quality is not measured.

## What is tested instead

- The gates (`tests/unit/gates.unit.test.ts`) and the adversarial fixture prove that unsafe or malformed proposals are rejected.
- The browser re-audit proves that an accepted value is present and that no new axe or keyboard finding appeared.
- `npm run test:live` runs the four fixture alt texts against a real model when `LLM_API_KEY` is set and asserts only that the
  proposals pass the gates, never their wording.

None of these says that an `alt` text describes the image well. That is a human decision, which is why every LLM-derived fix is
flagged for human review and never written by `--write`.

## Design of the planned evaluation (not built in v1)

It is designed so that a later milestone needs no open decision. It would measure, not assert.

- `fixtures/eval/alt-text.json`: 12 items `{ id, image, pageTitle, surroundingText, insideControl, reference: { kind, alt }, notes }`. Images
  are generated by a script (shapes, text labels, charts drawn with rectangles), so no third-party image is needed. 3 items carry an
  injected instruction in `surroundingText` and expect a normal alt.
- `fixtures/eval/control-name.json`: 8 items with markup, context and a reference name (icon-only buttons and links, one unlabeled search box).
- `scripts/eval-live.ts`: builds each input exactly as the strategies do, calls the real provider (2 attempts with gate feedback), runs the
  gates, and scores with a rubric computed by code: 3 passes the gates and contains every required keyword and no forbidden one; 2 misses one
  required keyword; 1 passes the gates but misses the point; 0 rejected by the gates after both attempts. The `kind` (informative or
  decorative) is scored separately. There is no LLM judge: the rubric is keywords and gates.
- The scorer is a pure function, to be unit-tested against hand-written proposals before any key is used.
- Output: this file, with the model, the base URL host, the date, the prompt version, n per task, the score distribution, the kind accuracy, the
  outcome of the three injection items and a per-item table. Numbers would be reported as "n=12, one model, one run".

## Limitation: synthetic images

The evaluation images would be synthetic. A model that describes a drawn chart well may still fail on a photograph of a product, so the
score would be a floor for plumbing and a weak estimate of quality on real sites.
